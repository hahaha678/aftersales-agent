# 转人工处理工单

这是异步人工处理流程：用户从聊天页面提交问题，客服领取、核实后回复并解决，用户到“人工工单”查看结果。不会停止 Agent、实时接管聊天，也不会因解决工单自动改变售后或退款状态。

## 使用步骤

1. 重启 local 后端，Flyway 自动执行 V8。前端保持 `npm run dev` 并刷新。
2. 买家打开智能售后中的一个会话，点击“转人工”。填写问题，可选择关联本人订单或售后申请（选择器提供最近100条）。
3. 核对共享聊天记录说明后提交，跳转到工单详情。已有未关闭工单时返回原工单，不追加或覆盖本次问题。
4. 客服登录后进入“客服工单”，打开待处理工单，阅读问题、聊天快照和关联售后，确认领取。
5. 领取客服填写用户可见的处理结果，确认“回复并解决”。买家在“人工工单”刷新查看结果。

状态为 OPEN（待处理）→ IN_PROGRESS（处理中）→ RESOLVED（已解决）。领取后仅当前领取客服能解决；其他客服可查看，不能抢占或覆盖。客服不能领取自己的工单。暂不支持转派、重开、在线聊天或追加多轮回复；解决后用户可从会话创建新工单。

## 业务与权限

- 身份从认证上下文获取。关联会话、订单、售后单均校验归属；同时关联订单与售后时必须属于同一订单。只选售后会自动关联它的订单。
- 工单拥有者可访问本人工单；客服通过独立 staff 接口查看队列、工单及其聊天快照。没有放开原聊天接口的跨用户权限。
- 提交事务复制当时已保存的消息到快照表。后续私人消息不加入快照，已有工单被复用时也不会更新快照。历史按消息 ID 分页读取，每页最多50条。
- 创建时锁定用户行，数据库生成列唯一约束进一步保证一个会话只有一个未关闭工单。重复提交用稳定 UUID；相同键不同内容返回409。
- 复用已有工单也记录请求键与内容指纹。因此该请求在工单解决后晚到重试，仍返回原工单，不意外创建新工单。
- 领取、解决使用工单行锁及条件更新，状态与审计事件在同一事务提交；同一客服重复领取、相同处理结果重复提交不会增加事件。
- 所有消息和处理结果以纯文本渲染。聊天回复只供客服参考，订单/退款结论应核对业务记录；不调用模型生成工单摘要或处理结果。

## 接口与表

| 接口 | 用途 |
| --- | --- |
| POST /api/tickets | 创建或复用工单，统一返回200 |
| GET /api/tickets | 本人工单，status可选，before为上一页末条ID |
| GET /api/tickets/{id} | 本人详情与处理记录 |
| GET /api/tickets/{id}/context | 本人提交时聊天快照，before为最早消息ID |
| GET /api/staff/tickets | 客服队列，同样支持状态及游标 |
| GET /api/staff/tickets/{id} | 客服详情 |
| GET /api/staff/tickets/{id}/context | 客服读取聊天快照 |
| PUT /api/staff/tickets/{id}/assignment | 当前客服领取，无请求体 |
| PUT /api/staff/tickets/{id}/resolution | 回复并解决，JSON字段 resolution |

创建字段：conversationId、requestKey、problem（1–2000字符），可选 orderId、aftersaleId；ID均使用字符串，避免前端大整数精度损失。列表最多50条，不包含详情事件。

V8 新增 support_ticket、support_ticket_event、support_ticket_submission 和 support_ticket_context。代码按 support/controller、service、mapper、domain/{dto,po,query,vo} 组织，保留4空格缩进及关键事务注释。
