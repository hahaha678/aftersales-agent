# 模拟退款闭环

客服确认收货后可执行模拟退款，并最终完成售后申请。所有流水以 `SIM-` 开头，不连接支付渠道、不产生资金变动。Agent 可以查询状态和流水，但没有退款写工具。

## 状态与操作

| 当前状态 | 操作或结果 | 下一状态 |
| --- | --- | --- |
| RETURN_RECEIVED / REFUND_FAILED | 模拟渠道立即成功 | COMPLETED |
| RETURN_RECEIVED / REFUND_FAILED | 模拟渠道明确失败 | REFUND_FAILED |
| RETURN_RECEIVED / REFUND_FAILED | 模拟渠道响应超时 | REFUND_PENDING |
| REFUND_PENDING | 查询原流水确认成功 | COMPLETED |
| REFUND_PENDING | 查询原流水确认失败 | REFUND_FAILED |

UNKNOWN 是退款流水状态，对应售后 REFUND_PENDING，不能当作失败直接重试。超时场景不会真的等待网络超时：提交时存为 UNKNOWN，客服点击查询时按已保存的模拟场景返回最终结果。普通 GET 详情只读，不推进状态；重复查询不重复记事件。

## 数据与可靠性

- V7 新增 `aftersale_refund`，保存请求键、前序失败请求键、独立模拟渠道编号、金额、模拟场景、状态、操作者和时间。详情返回全部流水，列表不加载流水明细。
- 退款金额只能取售后单的后端计算值，前端不能指定；再次检查该商品的成功/未知退款金额加本次金额不超过实付。
- 使用订单行锁串行化同一订单下的售后写操作。退款流水、申请状态和审计事件同事务提交。
- 一次请求携带稳定 UUID，相同键和相同内容重试不新增流水，改变内容返回 409。失败后的新尝试必须携带最近失败流水的 `previousKey`；旧页面或并发失败重试不能连续产生额外尝试。
- 未知、失败、完成状态均继续计入不可再次申请的数量和金额。完成状态表示这些数量已经处理，不能因结束售后而重新释放。
- 仅客服可发起或查询同步，禁止处理自己的申请。买家只能查询自己的详情和流水。
- 前端请求异常时保留原请求键与内容；刷新成功后重新依据后台流水核对。成功、失败、超时场景均可在客服页面选择。

这是本地确定性模拟渠道，渠道结果与业务数据一起保存在 MySQL 中。真实支付接入需要把发送和回查拆成独立流程，补充渠道签名验证、回调去重、后台补偿和对账；不能直接把远程支付 HTTP 调用塞进目前的数据库事务。

## 接口

`PUT /api/staff/aftersales/{id}/refunds/{requestKey}`：发起/幂等重放。

```json
{"mode":"TIMEOUT_SUCCESS","previousKey":null}
```

mode 为 `SUCCESS`、`FAILURE`、`TIMEOUT_SUCCESS` 或 `TIMEOUT_FAILURE`。requestKey 为小写 UUID。明确失败后需生成新 requestKey，并把最近失败的 requestKey 放入 previousKey。

`POST /api/staff/aftersales/{id}/refunds/{requestKey}/reconciliation`：查询并同步原模拟流水；无请求体。两个接口返回更新后的 AftersaleVO，并有 Swagger 注解。`refunds` 数组按最新优先，金额为字符串，时间使用 UTC 偏移。

## 本地联调

1. 重启 IDEA 的 local 后端，Flyway 自动应用尚未执行的 V6/V7；无需重建库或导入种子。
2. 前端保持 `npm run dev`，刷新页面。使用客服账号进入售后工作台，打开已确认收货的申请。
3. 选择“立即成功”，勾选确认并提交，应出现模拟流水和“售后完成 · 模拟退款成功”。买家详情能看到相同状态。
4. 用另一份已收货申请选择“响应超时，查询后成功”，提交后只提供查询入口；点击后变为完成。
5. 用失败场景验证：明确失败后能核对并重试；“响应超时，查询后失败”必须先查询，再重试。
6. 重复点击或刷新后查看同一成功记录，不能再次退款；已处理数量不能重新申请。

测试命令：`./scripts/Run-AgentBaseline.ps1 -AftersaleTest`。使用隔离 MySQL/Redis，不访问日常库、不调用 DeepSeek。新增测试覆盖成功幂等、超时两种结果、失败并发重试、权限、非法状态、分批金额及完成后数量限制。前端需要通过类型检查和生产构建；真实浏览器手工验收单独执行。
