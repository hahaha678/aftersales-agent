# 同一会话第二份草稿未显示：结果校验修复

## 实际原因

2026-09-29 对截图对应的演示会话进行了接口核对：草稿列表只有一份已确认的无线鼠标草稿；最近的聊天文字却声称鼠标垫草稿已生成。后台没有第二份草稿可供前端渲染。

前端本来就按草稿 ID 渲染多张卡片，并在回答结束后重新读取草稿列表；后端查询也按会话返回多条，不是一会话只能一份。模型的自然语言“已生成”不能作为数据库创建成功的证据。仅根据这次接口检查不能区分模型未调用工具还是工具未成功，因此修复同时覆盖这两种情况。

## 修复

- 新增 DraftReplyGuard，每次 DeepSeekGateway.stream 独立创建，历史成功回复不会成为新一轮的成功证据。
- 包装 createAftersaleDraft 的真实返回，只有无 error 且为 READY、含 id 的草稿结果才登记成功。
- 有成功结果时，用工具返回的订单、商品、数量、金额和描述生成统一确认提示；多份结果逐个列出，不使用模型自行编写的金额或“已提交”说法。
- 没有成功结果时，拦截“已为你生成草稿”“草稿如下”“确认卡片”等常见虚假成功文案，说明本轮未成功创建，而不是伪造卡片。
- 提示词要求新申请每轮实际执行创建工具，缺少商品内部 ID 时先查询订单，不能模仿历史成功回复。

这是写工具证据约束及常见文案保护，不是自然语言所有表达的完备分类器。未声称可以识别所有隐含成功表述，也未新增自动付费重试。后续若采用结构化动作结果，可进一步减少文本匹配的依赖。

## 使用与验证

重启后端后，再次明确发送商品、数量和原因请求生成。历史错误回复不会自动改写；系统也不会根据历史文字自动补建草稿或提交申请。最终以真实草稿卡片为准，每份草稿需单独确认。

测试覆盖：

- 模型未调用工具却回复成功、工具返回错误、只读工具返回类似结构时，不能作为新草稿成功依据。
- 工具真实创建成功时，确认提示使用真实金额和商品；两份结果都保留，重复相同 ID 不重复列出。
- 使用真实 Spring AI 适配器和本地模拟模型，验证虚假成功文字在到达 SSE 消费方之前被替换。
- 隔离 MySQL/Redis 下，同一会话先确认第一份，再生成不同商品的第二份，列表同时保留 CONFIRMED 和 READY 两份；第二份可单独确认，其他用户不能读取。

运行 `./scripts/Run-AgentBaseline.ps1 -AftersaleTest`，包含 Agent 集成与草稿校验回归，不调用真实 DeepSeek。此前 Agent 测试工具列表未包含后来新增的 searchPolicies，本次同步更新该断言，保留完整列表校验。
