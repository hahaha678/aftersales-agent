# RAG 真实评测基线 v1

执行日期：2026-09-29 15:55–15:56（北京时间）。使用本机 Ollama bge-m3、真实 DeepSeek 和隔离 MySQL/Redis，通过真实 HTTP/SSE、政策发布、检索与 Agent 工具链路完成 15 个场景。日常开发库的政策未修改，临时服务已关闭。

## 核心结果

**链路能正常运行，但 Agent 对政策问题的工具选择还不稳定。自动业务检查通过，不等于回答质量全部通过。**

| 指标 | 结果 | 口径 |
|---|---:|---|
| 任务正常完成 | 15/15 | 状态 SUCCEEDED |
| 无自动业务检查失败 | 15/15 | 来源原文对应、有效版本/范围、超期资格查询、不得建草稿等 |
| 原始问题直接检索目标文档 | 9/13（69.2%） | 人工预设 scope，阈值以上 Top-4；R11/R14 没有指定目标文档，排除分母 |
| Agent 实际取回目标文档 | 6/13（46.2%） | 同一目标集，但工具调用、问题改写和 scope 由模型选择 |
| Agent 调用政策检索 | 8/15 | 包括返回空结果的调用 |

工具调用和来源可用性指标不同于答案正确率。例如 R12 正确拒绝了编造承诺，但没有进一步查政策；它在安全行为上合理，在“取回目标文档”指标上仍是未命中。

## 关键问题与下一步

1. **先修工具选择。** R03/R07/R08/R09/R10 未查政策。应区分“一般政策咨询”和“具体订单办理”：一般政策问题先检索，只有判断订单状态、资格或建草稿才要求订单信息。这是本轮比调阈值更直接的改进点。
2. **检索改写有价值。** R02 和 R15 的原始问题未命中目标，但 Agent 改写后命中。后续固定问题改写策略，与当前基线对比；不能仅用两例宣称普遍提升。
3. **明确无结果的含义。** 没有达到阈值的结果不代表整个知识库没有相关政策。R04 需改成“本次没有检索到足够相关的依据”。后续检查漏召回的排名与分数，再调整 0.65 阈值，避免盲目降低后带来误召回。
4. **格式和时间交给代码。** R15 工具返回 `2026-09-28T07:56:19Z`，回答却写 `07:56:19（北京时间）`，正确北京时间应为 `15:56:19`。建议服务端提供已格式化时间，避免模型自行换算。
5. **区分原文和补充建议。** R01/R02 中的具体排查例子不是政策条款；若允许提供，应明确是一般性建议，不能伪装成知识库要求。R10 不应补充项目未实现的退款流程。
6. **引用展示更友好。** 目前正文仍出现 sourceId/sourcePath 等技术字段，前端已有来源卡片，后续可让正文仅保留标题和版本。

本轮仅建立基线，未修改提示词、检索阈值、政策正文或业务代码来追求更高分；R13/R14 的版本变更是预先定义的测试步骤，没有选择性重跑问题。

## 可复核配置与限制

- 对话模型：deepseek-flash，temperature=0.2，thinking 关闭，max_tokens=2048/请求，无自动重试。
- Embedding：bge-m3，本机 Ollama，digest `7907646426070047a77226ac3e684fbbe8410524f7b4a74d02837e43f2146bab`。
- 分块：600 个 Unicode 码点，重叠 80；相似度阈值 0.65，Top-4。当前资料很短，每份基本只形成一个片段，不能据此评价长文档分块效果。
- 初始语料只有 5 份演示政策，15 道自编问题，每题运行一次。没有覆盖大量干扰文档、多轮政策追问、复杂附件或文档间冲突。
- 原始检索使用人工给定 scope，Agent 实际选择的 scope/问题见工具记录。两者测的是不同环节，不混作一个准确率。
- 模型别名可能更新，开发工作区有未提交修改，源码哈希在 source-hashes.json；用量是供应商报告值。
- 执行器完成的 Maven 成功表示 15 个记录已产出，不表示所有效果通过。检查业务失败列表和人工审阅才能判断问题。
